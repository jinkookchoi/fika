# 상시 CPU 점유 · 메모리/포트 증가 진단 (2026-08-21, v1.18 기준)

"창이 하나도 안 보이는데 Fika가 CPU를 28~40% 먹는다"에서 출발해, 원인을 잡고(→1.18)
남은 메모리·mach port 증가가 누수인지까지 확인한 기록이다.
**결론: CPU는 해결됐고, 포트·메모리 증가는 누수가 아니라 지연 초기화 후 포화다.
다만 최초 관측된 5,225 포트는 재현하지 못했다.** 재점검 방법은 §7.

---

## 1. 요약 (TL;DR)

- **CPU 28~40%의 범인은 팝오버(패널) 상주 렌더였다.** 닫아도 `contentViewController`가 살아 있어
  SwiftUI가 `engine`을 구독한 채 보이지 않는 패널을 계속 그렸다. 여기에 이미지·집계 캐시 부재가 얹혔다.
- 1.18에서 다섯 가지를 고쳐 **팝오버 닫은 직후 17.8% → 7.5%**, 미개봉 11.2% → 8.8%(8Hz 적용 후 9.4%)가 됐다.
  7시간 25분 연속 가동한 프로세스가 **6.4%** 로, 시간이 지나도 오르지 않는다.
- **누수는 없다.** `leaks`가 잡은 건 총 1.5KB이고 그마저 전량 시스템 프레임워크(AppIntents/NSXPCConnection)다.
  heap 증가율은 시간당 약 360KB로, RSS 증가를 설명하지 못한다.
- 포트·RSS는 **첫 토스트(+213) · 첫 휴식 오버레이(+63) · 첫 팝오버 개폐(+133)** 에서 계단식으로 뛴 뒤
  **포화**한다. 유휴·반복 토스트·개폐 11회 이후·디스플레이 sleep/wake에서는 순증이 없다.
- **미해결**: 최초 관측된 5,225 포트(17일 가동)는 어떤 실험으로도 재현하지 못했다. 후보는 §5.3.

## 4. as-is / to-be 측정치

측정 조건은 **전부 재시작 직후 기준**이다. 화면 점등 유지(`caffeinate`), 12초마다 무해한 키 입력으로
"활동 중" 상태 유지(안 하면 자리비움으로 빠져 조건이 어긋난다), 동일 스크립트.

### 4.1 1차 (이미지·집계 캐시) — 팝오버 열림 60초

| 지표 | as-is | to-be |
|---|---|---|
| CPU | 23.0% | 20.5% |
| CPU 시간 / 60초 | 14.91s | 13.08s |
| `CA::Transaction::commit` (10초 sample) | 1,601 | 1,238 |
| 프로파일의 `MascotCut.image` | 17 샘플 | **0** |
| `SessionStore.thisWeek.getter` / `__getattrlist` / `NSImage.init(contentsOf:)` | 검출됨 | **0** |

### 4.2 2차 (팝오버 해제 + 상태아이템) — 구간별

as-is = 1차 수정본, to-be = 여기에 조치 4·5 추가. 각 구간 동일 스크립트.

| 구간 | as-is CPU | to-be CPU | 변화 | as-is ports | to-be ports |
|---|---|---|---|---|---|
| 팝오버 미개봉 (3분 경과) | 11.2% | 11.2% | — | 203 | 206 |
| 팝오버 열림 (60초) | 19.9% | 20.1% | — | 257 | 258 |
| **팝오버 닫은 직후 (40초)** | **17.8%** | **8.9%** | **−50%** | 256 | 257 |
| 개폐 5회 반복 시 닫힘 CPU | 14.6~16.8% | **7.4~8.0%** | −52% | | |

`AppDelegate.updateButton()` 샘플 수는 72 → 54(−25%)로 줄었으나, **미개봉 CPU 총량은 변하지 않았다.**
남은 비용은 앱 코드가 아니라 AppKit이 상태아이템 이미지를 교체할 때 하는 일(그림자 재생성 + CA 커밋)이다.

### 4.3 메뉴바 갱신 주기 실측 (프레임 건너뛰지 않고 주기만 변경)

|---|---|---|---|
| 0.1s | 10Hz | 8.4초 | 11.0~11.2% |
| **0.125s (채택)** | **8Hz** | **10.5초** | **9.4%** (2회·50샘플 평균, 범위 8.4~10.4) |

거의 선형이다. 더 낮추면 더 절감되지만 시각적 인상과의 교환이다.

## 5. 누수 조사 — 확실한 것과 추정의 경계

### 5.1 확실한 것 (관측으로 뒷받침됨)

**① Fika 코드에서 유래한 메모리 누수는 없다.**

```
Process 58295: 17 leaks for 1504 total leaked bytes.
  → 전량 <NSXPCConnection> ROOT CYCLE / Protocol: LNDaemonApplicationInterface
     (AppIntents · LNProcessInstanceRegistryClient — 시스템 프레임워크)
```

**② heap 증가율은 RSS 증가를 설명하지 못한다.** 25분 유휴 간격으로 두 번 뜬 `heap` 차이:

| 클래스 | 1차 → 2차 |
|---|---|
| non-object | 33,006 → 33,607 (+601, +108KB) |
| SwiftUI.DisplayList / EnvironmentValues | 36 → 59 / 35 → 57 |
| AGSubgraph / ViewFrame / AnimatableFrameAttribute | 각 31~33 → 45~47 |
| **NSImage / NSBitmapImageRep / CGImage** | 297/257/182 → **298/258/183 (각 +1)** |
| **총 노드** | 83,587 → 84,920 (**+151KB**) |

시간당 약 **360KB**. 7시간이면 2.5MB로, 관측된 RSS 25MB 증가와 자릿수가 다르다.

**③ `vmmap`의 `CG image` 261 리전(4.2MB)은 누수가 아니라 1.18의 프레임 캐시다.**
`NSBitmapImageRep` 258개 = 미리 구운 프레임 252장(84 × work/warning/done) + 컷 4장.

**④ 포트는 특정 "첫 이벤트"에서 계단식으로 뛴 뒤 포화한다.**
시간압축 60× 대조군을 시작부터 추적하고 `Fika.log` 타임스탬프와 대조한 결과:

| t | ports | 직전 이벤트 |
|---|---|---|
| 5s | 206 | 앱 시작 (아직 알림 없음) |
| 10s | **419** | ← **첫 토스트 표시 (+213)** |
| 45s | 492 | 토스트 반복 |
| 50s | **555** | ← **첫 휴식 오버레이, 화면 3개 (+63)** |
| 60~200s | 526~579 | 토스트 수십 회 더 — **순증 없이 진동만** |

**⑤ 유휴에서는 늘지 않는다.** 7시간 가동한 프로세스를 7분간 관찰: 515 → 523 → 513 → 513 → **513**.
이 프로세스는 1.18 실행 이후 **팝오버를 한 번도 연 적이 없는데** 이미 500대였다.

**⑥ 팝오버 개폐도 포화한다.** (압축 없이 신규 인스턴스, 개폐 30회)

| 개폐 | 0 | 5 | 10 | 15 | 20 | 25 | 30 |
|---|---|---|---|---|---|---|---|
| ports | 208 | 297 | 341 | 340 | 342 | 343 | **347** |

첫 10회에 +133, **그 다음 20회에 +6**. 조사 초기에 "개폐당 +6 순증"으로 본 것은 초기 구간과 진동의 오독이었다.

**⑦ 디스플레이 sleep/wake는 무관하다.** (3회 반복)

| | 전 | wake1 | wake2 | wake3 |
|---|---|---|---|---|
| 7시간 프로세스 | 541 | 530 | 530 | 530 |
| 신규 프로세스 | 346 | 348 | 348 | 348 |

**⑧ 1.17과 1.18의 포트 거동은 사실상 같다.** 이번 수정은 CPU만 잡았다(포트 쪽엔 잡을 누수가 없었다).

| 개폐 | 1.17 ports/RSS | 1.18 ports/RSS |
|---|---|---|
| 0 | 205 / 21M | 208 / 30M |
| 10 | 336 / 42M | 341 / 47M |
| 30 | **353 / 43M** | **347 / 51M** |

RSS가 1.18에서 +8MB 높은 것은 프레임 비트맵 캐시로, 의도한 교환이다(§6-3).

**⑨ 포트 수는 CPU를 유발하지 않는다.** 347 포트인 신규 프로세스와 541 포트인 7시간 프로세스 모두 CPU가 낮다.
17일 프로세스가 28~40%였던 것은 포트 때문이 아니라 팝오버 상주 렌더 때문이었고, 그건 1.18에서 해결됐다.

### 5.2 확인하지 못한 것

- **포트의 종류**: `lsmp -p <PID>`가 root를 요구해 `task_for_pid()`가 실패했다.
  종류별 내역을 보려면 `sudo lsmp -p <PID>`가 필요하다.
- **1.17에서 팝오버를 열어둔 채 장시간 방치**했을 때의 거동: 3.3분 방치에서는 343 → 343으로 평평했으나,
  그때 CPU가 6.4%로 낮아 팝오버가 실제로 열려 있었는지 확실하지 않다. **이 한 건은 결정적이지 않다.**

### 5.3 추정 — 5,225 포트는 재현 실패

관측된 포화 수준은 조건에 따라 **350~580**이다. 최초 관측치 5,225는 그 **약 10배**이며,
이번 조사의 어떤 실험으로도 재현하지 못했다. 남은 후보는 셋이다.

1. **시스템 전체 절전(system sleep)** — 디스플레이 절전과 달리 검증하지 못했다.
   재현하면 조사 세션 자체가 멈추기 때문에 시도하지 않았다. 17일 가동이면 매일 밤 겪었을 이벤트다.
2. **외부 모니터 물리적 연결·해제** — 화면 3개를 쓰는 환경이라 재구성이 잦다.
   사람이 케이블을 꽂았다 빼야 재현되므로 자동화로 확인할 수 없었다.
3. **아주 긴 시간대의 미세 증가** — 7분·3.3시간(압축) 관찰에서는 평평했지만,
   일 단위에서만 드러나는 느린 증가일 가능성을 배제할 수 없다.

**어느 쪽인지 가르는 방법은 §7.3에 있다.**

## 6. 알려진 제약 (1.18에서 감수한 것)

1. **외장 모니터 배율** — 메뉴바 프레임을 앱 시작 시점의 주 디스플레이 배율(`NSScreen.main?.backingScaleFactor`)로
   미리 굽는다. 1x 화면에서 켠 뒤 레티나로 옮기면 아이콘이 흐리게 보일 수 있다. **앱을 다시 켜면 해소된다.**
2. **SF Symbol 접근성 라벨** — 심볼 캐시 키가 심볼 이름뿐이라, 같은 심볼에서 `phaseLabel`이 바뀌어도
   처음 생성 시의 `accessibilityDescription`이 유지된다. (심볼 테마 + VoiceOver 사용 시에만 해당)
3. **메모리 +5~6MB** — 프레임 252장을 비트맵으로 미리 구운 대가. CPU와 맞바꾼 것이다.
   줄이려면 클립별 지연 생성(쓰는 클립만 굽기)으로 바꿀 수 있으나, 누수와는 무관한 별개 튜닝이다.

## 7. 재점검 방법

### 7.1 기본 측정 명령

```bash
PID=$(pgrep -f "MacOS/Fika")

# 가동 시간과 누적 CPU
ps -o pid,etime,%cpu,rss -p $PID

# CPU / RSS / ports / threads — 첫 샘플은 부팅 이후 누적이라 버리고 2번째부터 읽는다
top -l 6 -s 2 -pid $PID -stats pid,cpu,rsize,ports,th

# 메모리 영역별 (CG image / IOSurface / MALLOC_SMALL 등)
footprint -p $PID
vmmap -summary $PID

# 누수 판정
leaks $PID

# heap 증가율: 20~30분 간격으로 두 번 떠서 "All zones: N nodes (M bytes)" 비교
heap $PID > /tmp/heap1.txt      # ... 25분 후 ...
heap $PID > /tmp/heap2.txt
grep "All zones:.*nodes (" /tmp/heap1.txt /tmp/heap2.txt

# 핫스팟
sample $PID 10 -f /tmp/sample.txt
grep -oE "[0-9]+ [^[]*\(in Fika\)" /tmp/sample.txt | sort | uniq -c | sort -rn | head
```

> **측정 시 주의**: 화면이 꺼지거나 자리비움에 들어가면 CPU가 0.1%로 떨어져 비교가 무의미해진다.
> 조건을 맞추려면 `caffeinate -dimsu`로 점등을 유지하고, 12초마다 `osascript -e 'tell application "System Events" to key code 60'`
> (오른쪽 shift — 무해)로 활동 상태를 유지한다.

### 7.2 정상 / 이상 판정 기준

| 지표 | 정상 (조치 불필요) | 추가 조사 필요 |
|---|---|---|
| CPU, 팝오버 미개봉 | **8~10%** | 15% 이상이 지속 |
| CPU, 팝오버 열림 | ~20% | 30% 이상 |
| CPU, 팝오버 닫은 직후 | **7~9%** (미개봉 수준으로 돌아와야 한다) | 15% 이상 — 조치 4(뷰 해제) 회귀 의심 |
| CPU, 장시간 가동 | 시간이 지나도 안 오름 (7시간 25분에 6.4%) | 가동 시간에 비례해 오름 |
| mach ports | **350~580에서 포화** | **1,000 초과** |
| RSS | 30M(시작) → **43~56M에서 포화** | **100M 초과** |

| `leaks` | 2KB 미만, 전량 시스템 XPC | Fika/AppKit 객체가 목록에 등장 |
| `sample`에 등장하면 회귀 | — | `MascotCut.image`, `SessionStore.thisWeek.getter`, `__getattrlist`, `NSImage.init(contentsOf:)` |

### 7.3 5,225 포트 판정 — 관측 대상 PID 58295

**이 조사의 판단 근거로 프로세스 하나를 일부러 살려뒀다.**

| 항목 | 값 |
|---|---|
| PID | **58295** |
| 번들 | 1.18 (8Hz 적용본) |
| 시작 | **2026-08-21 01:11:46** |
| 조사 종료 시점 (08:37, 7시간 25분) | CPU **6.4%** / RSS **56M** / ports **567** / threads 18 |
| 조사 중 관측 범위 | ports 513~567 (진동), RSS 51~56M |

이 프로세스가 살아 있는 동안 며칠 뒤 `top -l 6 -s 2 -pid 58295 -stats pid,cpu,rsize,ports`로 다시 재고 판정한다.

- **ports가 1,000 미만이면** → §5.3의 후보 3(느린 미세 증가)은 기각. 포화가 확정되고 **누수 없음으로 종결**한다.
- **ports가 2,000을 넘으면** → 후보 1·2가 유력하다. 그 사이의 시스템 절전 횟수(`pmset -g log | grep -c "Entering Sleep"`)와
  모니터 연결·해제 여부를 함께 기록해 상관을 본다.
- **CPU가 15%를 넘겨 있으면** → 포트와 무관한 별개 회귀다. §7.1의 `sample`로 핫스팟부터 확인한다.

프로세스가 이미 종료됐다면, 새로 띄워 같은 조건(팝오버 한 번도 열지 않음)으로 며칠 재현해야 한다.

### 7.4 대조 실험을 다시 할 때

- **시간압축**: `FIKA_TIME_SCALE=60 ./Fika.app/Contents/MacOS/Fika` — 1초가 1분이 된다.
  세션 기록은 남지 않는다. 다만 **휴식 오버레이가 반복해 떠서 사용자를 크게 방해한다.** 짧게 쓰고 반드시 종료할 것.
- **대조군은 `open`이 아니라 바이너리 직접 실행**(`./Fika.app/Contents/MacOS/Fika &`)해야 별도 프로세스로 뜬다.
- **여러 인스턴스가 뜬 상태에서 특정 프로세스만 클릭**하려면 PID로 지정한다:
  `osascript -e 'tell application "System Events" to tell (first process whose unix id is <PID>) to click menu bar item 1 of menu bar 2'`
- 대조군은 **측정이 끝나는 즉시 종료**한다. 방치하면 알림·오버레이가 중복으로 뜬다.

## 8. 측정 원본

원본 로그는 세션 스크래치패드(`.../scratchpad/`, `scratchpad/leak/`)에 있었고 **세션 종료와 함께 사라진다.**
재점검에 필요한 수치는 전부 이 문서 §4·§5·§7에 옮겨 적었다. 원본 파일 구성은 참고용으로만 남긴다.

| 파일 | 내용 |
|---|---|
| `asis-*.txt` / `tobe-*.txt` | 1차(이미지·집계 캐시) 구간별 `top` 로그와 `sample` |
| `r1-*.txt` / `r2-*.txt` | 2차(팝오버 해제·상태아이템) 구간별 측정 |
| `hz-0.1/0.125/0.15.txt` | 메뉴바 갱신 주기별 CPU |
| `leak/heap1.txt`, `heap2.txt` | heap 25분 간격 2회 |
| `leak/vmmap1.txt` | 영역별 요약 |
| `leak/ctrlC-trace.txt` | 시간압축 대조군 시작부터의 포트 추이 (§5.1-④의 근거) |
| `leak/d117-cycle.txt`, `d118-cycle.txt` | 1.17 / 1.18 개폐 30회 비교 |
| `leak/dual.txt` | 7시간 프로세스 유휴 관찰 |

앱 자체 로그는 `~/Library/Logs/Fika/Fika.log`에 계속 쌓인다(디버그 모드면 상태 전환·오버레이 동작까지).
§5.1-④의 이벤트 대조는 이 로그의 타임스탬프와 포트 추이를 맞춘 것이다.
